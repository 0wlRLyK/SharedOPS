# Cross-module transaction contracts

`dev.sharedops.household.contract.HouseholdTaskAccess` is exported as named interface `task`; add `household::task` to task's allowed dependencies. It exposes `<T> T withLockedHousehold(UUID householdId, Function<LockedHousehold,T> action)` with mandatory existing transaction, authenticated active actor, indistinguishable absent/inaccessible household, and lock held to transaction end. `LockedHousehold` exposes `UUID actorAccountId()`, `String timezone()`, `Optional<UUID> activeMembershipId(UUID accountId)`, `boolean isActiveMembership(UUID membershipId)`, and `Optional<UUID> historicalAccountId(UUID membershipId)`. View methods reject use after callback. Back with existing household stores/locking, not a task query of household tables. Membership changes must take the same household lock. Do not weaken existing named exports.

`dev.sharedops.responsibility.contract.ResponsibilityTaskAccess` is exported to task. In an already authorized transaction while caller holds household lock, `Optional<Snapshot> lockForTask(UUID householdId, UUID responsibilityId)` locks by both IDs and returns immutable `Snapshot(UUID ownerMembershipId, Status status, Mode mode)`, or empty for foreign/missing. `Status` distinguishes ACTIVE, PAUSED, ARCHIVED; `Mode` is INDIVIDUAL in M0. Lock remains until transaction completion. Task validates ACTIVE/INDIVIDUAL, then checks owner membership in locked household. This contract exposes no repository. Task service is responsible for authorization before invoking it; document precondition and enforce it with transaction/architecture tests. The lock order everywhere is household → responsibility → task. Direct application access is tested for foreign and unauthenticated actors.

Task application owns an immutable `Task` and `TaskStore` port. Store operations insert, lock by household and id, and compare-and-set update by `(householdId, id, expectedVersion)`, atomically insert edit facts and preserve existing checklist relationships. API adapters preserve three-way assignee choice: omitted, explicit unassigned, and specified account. The task service runs each command and projection within one transaction and returns only after successful store operations; DTO projection translates membership IDs with the locked household view. No public HTTP identifier is treated as proof of access.
