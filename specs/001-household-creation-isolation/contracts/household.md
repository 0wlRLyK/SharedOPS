# Proposed household contracts

**Status**: design contract pending review against the current candidate and [authoritative OpenAPI](../../../docs/api/openapi.yml); it does not itself prove implementation or verification. [Plan](../plan.md) | [Research](../research.md)

## Public interface

Proposed resource family under `/api/v1/households`:

| Operation          | Proposed contract                                                                                                                                     | Principal outcomes                                                                                                                                                              |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Create             | `POST /api/v1/households`, body with required `name` and `currency`, optional `icon` and `timezone`; authenticated account is not supplied by client. | `201` with `Location` and `id`, `name`, `icon`, `currency`, `timezone`; `400` validation; `401` unauthenticated; `403` CSRF; `409 ACTIVE_HOUSEHOLD_EXISTS` when already active. |
| Read own household | `GET /api/v1/households/{householdId}`                                                                                                                | `200` for active member; `404` for absent or inaccessible household; `401` unauthenticated.                                                                                     |

Read returns `id`, `name`, `icon`, `currency`, `timezone`; absent icon is `null`. For `name` and `icon`, whitespace means the Unicode White_Space code points U+0009–U+000D, U+0020, U+0085, U+00A0, U+1680, U+2000–U+200A, U+2028, U+2029, U+202F, U+205F and U+3000, including non-breaking spaces; trim only leading/trailing such code points from `name`. Require 1–100 Unicode code points afterward, preserving internal whitespace and case. `icon` omitted or `null` means no icon; reject empty or whitespace-only strings; otherwise retain the supplied string unchanged, up to 100 Unicode code points. No icon catalogue validation is performed in M0. Currency is required and must be exactly one of `EUR`, `UAH`, `USD`, `GBP`, `PLN`, `CHF`, `CZK`, `DKK`, `NOK`, `SEK`; reject missing, lower-case and all other codes, including valid ISO codes outside this list. There is no default or normalization; list changes require a reviewed contract update and release ([decision](../research.md#currency-and-financial-history)). Missing timezone defaults to `Europe/Berlin`; null, empty, invalid or offset-only timezone is rejected. Household data is not editable after creation in M0. If a later settings mutation is introduced during M0, timezone is not an accepted field: if supplied, reject the entire request as a 400 validation error without changing state. If M0 has no settings mutation, no endpoint is added just for this check; all implemented operations must reject attempts to change timezone without modifying state. Existing authentication and unsafe-request CSRF rules apply.

## Isolation and errors

All errors use existing Problem Details conventions and stable codes. For the same authenticated caller, operation and valid-form inputs, absent and inaccessible IDs yield equivalent `404 NOT_FOUND` in status, content type and stable problem fields, with no household resource payload, resource identity or observable metadata that reveals existence; the standard Problem Details body is returned. For these 404 responses `title` is `Not Found`, `status` is `404`, `detail` is `Resource not found.`, and `code` is `NOT_FOUND`; values are identical; omit `instance` and additional diagnostic fields. Compare status, media type and standard fields and code; no response metadata may reveal resource existence. A malformed identifier yields 400 `VALIDATION_ERROR` without echoing its value. Invalid JSON, validation and unauthenticated cases follow existing OpenAPI and are not substituted for the valid-ID comparison. Denied mutations and attempted foreign references must leave all affected committed data unchanged.

## Application boundary

Every public application operation derives authenticated account identity from the same trusted server-side context; an arbitrary caller-supplied account ID or household claim is not proof of authority. A missing, anonymous, unauthenticated or unexpected principal is rejected before persistence. Creation requires authentication and verifies that the account has no active membership; it does not require existing membership. Every operation scoped to an existing household resolves active membership per invocation and verifies that the target belongs to that scope before reading or mutation, including related IDs. A direct service caller is subject to the same policy. Stateless singleton services keep no mutable actor or household context. Cross-module consumers use documented exports, never another module's repository.

## Named Java module interface and compatibility

Replace the exported `boolean HouseholdLookup.existsById(HouseholdId id)` with `boolean HouseholdLookup.isAccessible(HouseholdId id)`. Keep `household::lookup` and propagated `HouseholdId`, but remove the unsafe old method rather than retaining an identity-free compatibility path. The operation obtains the authenticated account from the trusted server security context each call; it never accepts a client-selected actor ID or unverified scope. Return `true` only when this account has an active membership in the requested household. Return `false` identically for absent/anonymous authentication, null input, missing household, foreign household, or absent/inactive membership. Before any persistence read, reject an absent/anonymous identity. With a real identity, query only matching active membership; do not query global household existence. The implementation is an application service backed by an internal membership port, not an exported persistence adapter; no per-request identity is stored in singleton fields.

This is a source/binary and semantic breaking Java contract change. Repository graph/search found no in-tree production callers, but cannot establish absence of downstream consumers. Migrate discovered consumers, update module export architecture tests and `docs/architecture.md`, record the new semantics and required client migration, and obtain owner compatibility approval of the revised plan. Separate privileged/background access is outside this contract and needs a future reviewed design. Direct integration tests invoke this actual named interface, not a wrapper or stub, using trusted authentication contexts and production migrations. They assert owner success, foreign/missing/inactive/no-auth/null indistinguishable denial, no reads for no-auth and unchanged committed state, plus interleaved/concurrent context isolation.

## Transaction boundary

Creation is one public Spring-proxy-visible service operation, entered externally rather than via self-invocation. It persists household and initial active membership through injected ports/adapters within one transaction. A real failure after a persisted write must result in neither committed row. The DB's partial unique index handles concurrent requests; errors are mapped after rollback and must not leak constraint names. Tests observe fresh committed state without test-managed rollback.

## Compatibility and unresolved choices

The proposed endpoints are additions; the specified `Location` points to the created household; assess optimistic concurrency requirements before any later mutation with OpenAPI and owner. Agree and implement the financial-history check before releasing currency changes; document timezone validation and conditional edit behavior in the authoritative contract as part of implementation. Review existing API clients and migration preconditions before declaring compatibility. The authoritative OpenAPI and actual candidate must be reconciled with this contract; this document is not evidence of production behavior.
