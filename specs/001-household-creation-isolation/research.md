# Research and decisions: HO-10

**Status**: Proposed design research, rechecked 2026-11-19 at baseline `7570ec7fa74e0c0c9f7f4f328adb6ea028179840`. Conversation decisions below are distinguished from proposals and unresolved policy. This revision awaits owner plan approval.

## Authorization and concurrency

**Decision, owner-selected**: Application operations derive authorization from authenticated account and active membership; PostgreSQL constraints protect data invariants. No mutable current identity on singleton services. **Reason**: covers non-HTTP callers and races. **Alternatives**: controller-only checks cannot protect direct calls; row-level security adds connection context complexity and was not selected for M0. Sources: [constitution III](../../.specify/memory/constitution.md), [HO-10](https://linear.app/home-0ps/issue/HO-10/implement-household-creation-and-data-isolation).

**Design**: Use one externally invoked Spring proxy-visible transaction for both writes, with a database unique constraint on active membership. A check alone cannot serialize concurrent attempts. A real workflow failure after a write must roll back both; test with fresh committed-state reads. Transaction boundary placement must preserve module boundaries and prevent self-invocation bypass.

## Currency and financial history

**Decision, 2026-11-18**: M0 uses a fixed, explicitly supplied enum: `EUR`, `UAH`, `USD`, `GBP`, `PLN`, `CHF`, `CZK`, `DKK`, `NOK`, `SEK`. The first five were specified by the owner; the other five were selected for the European pilot within the owner’s request. Reject all other values, including otherwise valid ISO codes, lower-case and missing values; no default or normalization. The application uses no runtime currency-list service. Changes to the list require review, tests, a contract update and a release. Review stored values and migration compatibility before any removal; never silently rewrite existing household currency. [ISO 4217](https://www.iso.org/iso-4217-currency-codes.html) defines the codes; this deliberately limited product list supersedes the earlier broad current-code proposal.

[FR-HH-06](../../docs/requirements.md) permits selection before financial records. [D13](../../docs/decision-register.md#d13) is **deferred to M2** and proposes permanent freeze after the first-ever record, including deleted records; it is not an accepted M0 rule. The former issue wording included changes under a financial-history policy, while M0 has no implemented finance records. **Decision, owner-selected**: Do not release currency changes until the financial-history check is agreed and implemented. Creation with an initial currency remains in scope. The owner allocated currency-change acceptance to HO-50; it is not an HO-10 completion dependency. Do not use a hardcoded “no records” answer as proof of a financial-history check.

## Existing data and migration

**Decision, owner-selected**: Stop the new migration when any old `households` rows exist. Do not delete, assign an account, or manufacture a currency. A separate owner-approved migration/remediation is required before retry; dependent task and responsibility rows must be preserved. Test an empty upgrade and the failure case on existing data, including unchanged schema/data after failure. V1–V6 remain immutable; use the next available Flyway version at implementation time. Sources: [database](../../docs/database.md), [V1](../../backend/src/main/resources/db/migration/V1__create_core_persistence.sql).

## Baseline inspection and failure classification

Graph inspection at the historical intake baseline found `HouseholdEntity` contains only a UUID, `HouseholdPersistenceAdapter` implements `HouseholdLookup.existsById` only, and the household API has account and password controllers but no household operations. `AuthenticatedAccount.accountId()` carries server-derived identity into API code; `PasswordController` demonstrates the principal cast and passes the ID per call. `SecurityConfig` requires authentication for unlisted routes and enables session CSRF. V1 creates households and dependent task/responsibility foreign keys, V2 creates accounts, and migrations ended at V6 at that baseline. OpenAPI has a planned task GET but no household operations. The named `HouseholdLookup.existsById` contract is implemented directly by a persistence adapter and exposes arbitrary household existence without caller or membership; it is an authorization defect, not an operation to exempt from the criterion.

**Decision**: Keep the public create transaction proxy-visible and perform the insert pair on that same transaction. Translate only the named active-membership uniqueness constraint after rollback; unrelated integrity errors must propagate. A flush after the first write provides a deterministic real-workflow failure point for a test-injected membership-port fault. A separate regression sensitivity experiment must invoke the actual target without transactional advice, demonstrate the atomicity assertion detects the leak, then restore the real path and pass; do not ship a synthetic production endpoint. Tests observe post-completion data using a fresh connection and no test-managed rollback.

**Compatibility**: existing rows prevent migration; do not silently synthesize owners or settings. Empty-schema migration adds settings and membership. M0 endpoints are additive to the hand-maintained OpenAPI; no claims are made about previously deployed client compatibility until review. HO-15/HO-87 are no longer prerequisites by owner decision 2026-11-19; unavailable required CI evidence remains explicit.

## ANALYZE-C1: exported lookup and compatibility

**Decision previously approved by the owner, subject to current plan review**: replace `existsById(HouseholdId)` with `isAccessible(HouseholdId)`, resolve the authenticated actor from trusted server-side execution context inside an application boundary and answer only active-membership visibility. A scoped membership query can return `false` for foreign, nonexistent or inactive cases without querying unrestricted household existence; missing authentication returns `false` before persistence. A null input also returns `false`. The public contract never accepts a caller-supplied account ID as authorization proof. Named module export and `HouseholdId` propagation remain, but source and binary compatibility are intentionally broken; the old unsafe signature and unchecked overload are removed.

**Rationale**: The prior plan mistakenly retained a global existence oracle, contrary to the approved spec and issue direct-application-operation criterion. Returning identical denial for inaccessible and nonexistent inputs preserves concealment, including non-HTTP calls. A managed security context avoids mutable singleton identity and ensures HTTP and direct callers use the same application policy. Background/system access without a real authenticated account requires a separately approved system-identity contract; it is not invented here.

**Evidence and limits**: Graph search identifies the `@NamedInterface(value = "lookup", propagate = true)` interface and its raw persistence adapter; qualified inbound trace finds no callers. A focused repository text search finds its definition/implementation, the module export architecture test and task's allowed dependency, but no application call. Graph coverage and the checkout cannot exclude external/downstream callers. Update `docs/architecture.md`, architecture tests and any discovered consumers; document required API migration and obtain compatibility approval before integration. Keep the old interface out of exports and test against regression.

**Alternatives**: retaining the old method (even as deprecated) leaves an oracle; an overload accepting raw account UUID lets an untrusted caller claim another actor; both fail the stated boundary. A privileged existence API with separate system authorization may be designed later if a real need appears, with independent approval and tests.
