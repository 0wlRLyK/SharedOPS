# Implementation Plan: HO-10 household creation and isolation

**Status: proposed, awaiting independent review and owner approval.** This is a design, not evidence of implemented or verified behavior. The approved spec does not approve this plan.

**Branch**: `codex/ho10-batch5` | **Date**: 2026-11-19 | **Spec**: [approved specification](spec.md)

## Summary

Implement creation of a household and its initial active membership atomically and provide active-membership-scoped access to available operations. Preserve the existing modular architecture and prove authorization, transactional and race behavior against PostgreSQL. The owner has explicitly preserved the M0 scope: real joining is HO-11 and currency changes require the later agreed M2 financial-history policy. The owner allocated joining and create/join races to HO-11, currency change to HO-50, and future operation isolation to the issues introducing those operations. Their evidence is not an HO-10 acceptance prerequisite; all current M0 criteria remain mandatory.

## Technical Context

Java 25, Spring Boot and Modulith, PostgreSQL 18, Flyway and Testcontainers are documented in [stack](../../docs/stack.md) and [database](../../docs/database.md). Historical graph inspection at baseline 7570ec7 confirms `HouseholdEntity` contains only an ID; `HouseholdPersistenceAdapter` directly implements the named public `HouseholdLookup.existsById(HouseholdId)`, querying a repository without actor or membership; this is an unauthorized existence oracle and must be replaced. `AccountPrincipal` implements `AuthenticatedAccount.accountId()`, already used by `PasswordController`; `SecurityConfig` authenticates all non-public routes and applies session CSRF. Household API has account and password controllers, not household operations. V1 creates households and dependent foreign keys; V2 creates accounts; V6 is latest migration. Baseline OpenAPI has no household operations and marks task GET planned. No performance target is asserted.

## Design and constraints

- The actual creation flow must use HTTP controller → application service → port → persistence adapter with constructor injection and no synthetic production endpoint. Creation and initial active membership are one transaction entered through a Spring-visible proxy, and regression coverage must detect accidental self-invocation bypass.
- PostgreSQL must enforce at most one active membership per account under races. A genuine failure after an actual creation write must leave no committed household or membership; observe through a fresh transaction without test-managed rollback. Avoid conflating arbitrary database failures with the specific active-membership conflict.
- Resolve active membership for every available existing-household use case before access or effects, including direct exported calls and foreign IDs in requests and relationships. A service singleton keeps no request identity state. Parameterize applicable real HTTP endpoints and use deterministic coordinated interleaving/concurrency with authorized controls and committed-state assertions.
- Use [contract handoff](checklists/requirements.md#передані-вимоги-до-контракту): 201 response, Location and fields, 409 conflict, malformed ID 400, and equivalent foreign/absent/inactive 404 problem responses. The authoritative OpenAPI must be updated and compatibility assessed. The application must reject timezone edits in M0; where a settings endpoint exists the entire request must fail with 400 and no state change. If no such endpoint exists do not create one merely to test this case.
- Preserve fixed supported currencies, exact Unicode normalization and length limits, IANA validation and default semantics from the spec. Do not create a currency-edit operation without the agreed M2 financial-history policy and implementation.
- A new Flyway migration must stop on any preexisting household rows, preserving all existing household and related data and schema; remediation requires separate owner approval. Test both empty upgrade and populated failure with production migrations and observable committed state.

### Named household lookup remediation (ANALYZE-C1)

Replace `boolean HouseholdLookup.existsById(HouseholdId id)` with `boolean HouseholdLookup.isAccessible(HouseholdId id)`. This is a **source and binary incompatible Java module-contract change** and a semantic change: it answers visibility to the current authenticated account, never global existence. The existing named `household::lookup` export and propagated `HouseholdId` remain; `task` may depend on that interface. No obsolete overload or public identity-free existence operation remains. At baseline graph inbound tracing found no callers; a focused repository search found only the adapter implementation, the named-interface architecture test and `task/package-info.java`'s permitted dependency, plus documentation. This is evidence of no in-repository runtime caller, not proof that external or downstream consumers do not exist. Update architecture documentation and module export tests, search the complete candidate for callers, and explicitly record the migration from `existsById(id)` to `isAccessible(id)` in compatibility evidence and release notes; downstream clients must be identified and updated before integration/deployment. Do not silently claim this breaking contract is compatible.

Place the implementation behind a household **application boundary**, not a persistence adapter exported directly. It derives account identity from the authenticated server-side security context on every invocation through an injected identity-resolution port; never accept account ID, membership or household scope from an untrusted request as proof of authority. Missing/anonymous authentication, missing or inactive membership, foreign household, absent household, and null input all produce `false` without target details; an active member of the requested household gets `true`. For an absent or anonymous authenticated identity, return `false` before a household or membership read. For authenticated calls, query only the active membership relation for the trusted actor and requested household; the membership foreign key establishes household existence, so the exported operation never runs an unrestricted household-existence query. Any later cross-module consumer obtains authenticated context at its own trusted entry point; service identities and background execution require a separately reviewed policy, not a bypass. Maintain no mutable principal/household state in a singleton. Protect the remaining repository-level existence API as internal persistence infrastructure and do not export it through other module contracts.

Direct integration tests invoke the **actual named exported interface bean** without an HTTP controller using fresh, committed PostgreSQL fixtures and the production migrations. Exercise active owner → `true`, second active household actor → `false`, foreign ID and same-form absent ID → identical `false`, missing/anonymous authentication → `false` with no repository access, authenticated principal of unexpected type → denied without exception leakage, inactive membership → `false`, null → `false`, concurrent/interleaved authenticated calls → no context crossing, and snapshot all relevant committed household/membership data before and after denials to prove no mutation. Include a deliberately bypassed actor-filter mutation or equivalent test double in an isolated test run to establish these assertions fail, then restore and rerun. Separately test Spring Modulith still exposes only the authorized `lookup` contract and intended `HouseholdId`; compile and architecture checks must fail if an identity-free `existsById` overload is reintroduced. Cover the real GET endpoint and direct scoped service with equivalent foreign/absent 404 results as previously specified. This does not pretend the Java API has remained compatible or that unimplemented operations have been tested.

## Project Structure and task decomposition

Feature artifacts: [research](research.md), [data model](data-model.md), [contract](contracts/household.md), [verification guide](quickstart.md); `tasks.md` belongs to the later tasks stage. Keep source under `backend/src/main/java/dev/sharedops/household/{domain,application,api,infrastructure/persistence}` and real tests under `backend/src/test/java/dev/sharedops/household` and `backend/src/test/java/dev/sharedops/security`; migration under `backend/src/main/resources/db/migration/V7__*.sql`, contract additions in `docs/api/openapi.yml`. Existing authentication, error advice and architecture tests remain in their existing packages.

1. **Shared persistence contract and migration**: define creation/membership port interfaces in household application, data types for normalized create input/result and scoped lookup. Add V7 settings/membership and named partial unique index on active `account_id`, account/household foreign keys, preflight empty household table, and Hibernate mappings. Positive empty migration and populated preflight-failure tests compare schema and committed dependent data. Replace the exported identity-free `HouseholdLookup.existsById(HouseholdId)` contract and adapter implementation with the authorized visibility contract described below; do not retain an unchecked compatibility overload. Update affected architecture assertions and `docs/architecture.md` as part of the implementation.
2. **Use cases and transaction**: a public proxied `CreateHouseholdService.create(command)` resolves the authenticated account using a constructor-injected identity port, checks active membership, persists household and initial membership, flushes and returns the result inside one transaction. A separate scoped read `GetHouseholdService.get(householdId)` obtains the authenticated account from the same trusted context and resolves active membership before retrieving household; inaccessible or missing uses the same domain outcome. Neither public service trusts a caller-supplied account ID; internal persistence ports receive the verified account ID explicitly per invocation. Missing or anonymous authentication is rejected before persistence. Translate only the named partial-unique-index conflict after the transaction rolls back, including flush/commit timing; preserve all other integrity errors. Ownership can use an outer non-transactional entry/advice, not a catch inside a doomed transaction. All framework dependencies remain out of domain.
3. **Real HTTP and contract**: add household API controller and DTO/validation in `household/api`, using the same trusted identity-resolution boundary for direct and HTTP callers; add `POST /api/v1/households`, `GET /api/v1/households/{householdId}` and documented error mapping, with no update operation in M0. Update authoritative OpenAPI and check additive compatibility. Test exact agreed normalization, Unicode code-point counting, ten currencies, timezone omitted versus null/empty/offset-only, `201` location/body, CSRF/401, `409`, malformed ID and indistinguishable `404` responses. Do not accept client-supplied actor or household scope as authority.
4. **Behavior and security verification**: parameterize all actual scoped HTTP operations across allowed/foreign/missing/inactive cases; invoke exported services directly and inspect committed state after denied calls. A genuine membership-write fault after a flushed household write must propagate from the actual proxied service and leave neither record committed on a fresh connection, with no enclosing test transaction. Demonstrate sensitivity separately by intentionally invoking the real target outside its proxy, observing the atomicity assertion fail and an orphan after the independently committed first write, then restoring production proxy invocation and rerunning; no bypass path is shipped. Race real concurrent creates for one account using barriers, assert one winner and no orphan; interleave and concurrently execute two identities with allowed controls, inspect committed state. Real joining and create/join races belong to HO-11; future mutation verification belongs to the corresponding operation owners.
5. **Integration and evidence**: test the combined feature and contract against production Flyway, audit API/DB compatibility, record AC-to-test/command/result/revision coverage and open dependencies, then full local `make check`, `make test`, `make verify` and changed-document formatting under the workflow. Independent reviews and isolated implementation worktrees remain mandatory. Use test-first cycles for meaningful behavior and negative cases; task designer owns exact slices and checkboxes.

The task design pins interface signatures and ownership and includes each real observable assertion. The historical design above must be reconciled with the implementation and the current candidate before acceptance. Candidate manual mutation-sensitivity experiments must be isolated and fully restored before review. The suite must not assert absent endpoint behavior as if it existed.

## Compatibility, risks and open gates

- The named Java `household::lookup` contract is intentionally source/binary incompatible as described above; unknown external consumers require explicit migration and compatibility sign-off.
- API operations are additions to the currently authoritative OpenAPI and must be reviewed with client behavior, CSRF and status/error schemas. Exact agreed conditional `400` for a future M0 settings endpoint is preserved in the [contract](contracts/household.md).
- V7 rejects nonempty legacy households without deleting or changing dependent rows; rollout of existing data needs separate owner-approved remediation. Keep V1–V6 immutable. Database uniqueness plus application checks provide independent race and authorization protections.
- HO-10 acceptance covers only actual M0 operations. HO-11 owns joining/create-join races, HO-50 owns currency-history behavior, and later operation owners must enforce and test isolation. No synthetic endpoint or hardcoded absence of financial records substitutes for evidence on actual operations.
- HO-15 and HO-87 are not prerequisites to start per owner decision; unverified required remote CI must remain visible and cannot be claimed passing. All locally required checks and exact-revision evidence remain mandatory. Owner approval of this plan and all applicable gates precedes implementation.
