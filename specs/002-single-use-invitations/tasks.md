# Tasks: Single-use household invitations

**Input**: [spec.md](spec.md), [plan.md](plan.md), [data-model.md](data-model.md), [contract](contracts/invitations.md), [quickstart.md](quickstart.md); HO-11. The approved spec and plan are authoritative. Each task owns behavior and its regression tests; in the selected batch strategy workers write tests and the orchestrator executes them during final verification.

**Format**: `[ID] [P?] [Story] Description`. `[P]` identifies an opportunity only when prerequisites are integrated and scopes do not conflict. ## Phase 3: User Story 1 — Invite and join (P1)

**Goal**: An eligible account joins atomically and consumes a single-use invitation. **Independent test**: create, accept, inspect committed membership and consumption, then reject reuse without changes.

- [x] T003 [US1] Define the invitation application ports, models, exceptions and proxy-visible transactional operations in `backend/src/main/java/dev/sharedops/household/application/`, using `InvitationToken` and existing identity/household/membership ports. Implement authorized creation with 24-hour controlled clock, authorized transactional revocation under household-then-invitation locks, and transactional acceptance under the same lock order; enforce current-time checks after lock acquisition, capacity and active-account checks, atomic membership/consume, narrowly translated expected conflicts outside the failed transaction, and no secret logging; include meaningful creation, revocation and acceptance unit tests in `backend/src/test/java/dev/sharedops/household/application/InvitationServiceTest.java`. Define stable interfaces consumed by T004 and T005; no controller-only authorization.
- [x] T004 [US1] Implement the invitation JDBC adapter and any necessary persistence-only supporting classes in `backend/src/main/java/dev/sharedops/household/infrastructure/persistence/`, implementing T003 ports with required lock order, conditional state transitions, digest-only storage, and slot allocation; add `backend/src/test/java/dev/sharedops/household/infrastructure/persistence/InvitationPersistenceIT.java` covering persistence, terminal exclusivity and rollback-relevant behavior with production migrations.

## Phase 4: User Story 2 — Control an unused invitation (P1)

**Goal**: Authorized revocation and expiry prevent joining without private-data disclosure. **Independent test**: revoke and expire distinct invitations and inspect unchanged committed state after rejection; compare foreign and absent authorization responses.

- [x] T005 [P] [US2] Implement the approved HTTP contract in `backend/src/main/java/dev/sharedops/household/api/` and `docs/api/openapi.yml`: authenticated and CSRF-protected create, revoke and accept routes, exact documented success/error status and schemas, generic invalid token and inaccessible/absent outcomes, body-only secrets, no-store and no secret-bearing logs, exceptions, URLs or Location headers; include API-layer unit tests in `backend/src/test/java/dev/sharedops/household/api/InvitationControllerTest.java`. Use T003 interfaces; do not implement persistence or domain rules in controllers.
- [x] T006 [P] [US2] Add committed-state lifecycle and application-boundary integration tests in `backend/src/test/java/dev/sharedops/household/application/InvitationLifecycleIT.java` for valid join/reuse, successful acceptance just before the 24-hour deadline with committed membership and consumed invitation, rejection exactly at 24 hours and invalid/revoked/consumed tokens, authorized revocation, foreign/absent access, already-active account, atomic rollback after genuine failure between membership insert and consume, with a proxy-bypass-detecting control demonstrating that the atomicity test detects bypass of the real transaction boundary, digest-only storage and no token/URL in captured logs. Use production migrations, actual proxied services, controlled time, fresh connections and synthetic fixtures.

## Phase 5: User Story 3 — Preserve limits during simultaneous operations (P1)

**Goal**: Concurrent operations preserve household and account membership limits and atomic state. **Independent test**: run coordinated independent PostgreSQL transactions and inspect committed state after each outcome.

- [x] T007 [P] [US3] Add real PostgreSQL race coverage in `backend/src/test/java/dev/sharedops/household/application/InvitationRaceIT.java`: two invitations for the final slot, competing acceptance of one token, revocation versus acceptance, and household creation versus invitation acceptance for one account; synchronize actual transaction entry with bounded barriers/latches, inspect committed membership/invitation/household state, assert at most one new member, at most two active household members, no orphan and no loser-caused consumption. Also hold the household lock while an acceptance starts before expiry, advance the clock to its deadline, release the lock and prove rejection without committed changes. No sleeps or test-method rollback as proof.
