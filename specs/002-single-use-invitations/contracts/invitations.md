# Invitation interface contract

This is the planned additive contract; implementation must add equivalent definitions to `docs/api/openapi.yml`, the authoritative public HTTP contract, and validate the actual HTTP surface. All operations require existing authenticated session and CSRF protection for unsafe methods. Never transmit a secret in a path, query, log, error, redirect or Location header.

| Operation                                                            | Request                               | Success                                                                                                     | Failure                                                                                                                                                                                                                                           |
| -------------------------------------------------------------------- | ------------------------------------- | ----------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /api/v1/households/{householdId}/invitations`                  | No body; authenticated active member  | `201`, JSON `{id, token, expiresAt}`; `Cache-Control: no-store`; token returned exactly once                | `401` unauthenticated; `403` CSRF; `404` inaccessible or absent household, indistinguishable; `400` malformed ID                                                                                                                                  |
| `DELETE /api/v1/households/{householdId}/invitations/{invitationId}` | No body; authenticated active member  | `204` when unused invitation is revoked                                                                     | `401` unauthenticated; `403` CSRF; `404` absent/inaccessible household or invitation; `409` invitation already consumed or revoked; `400` malformed ID                                                                                            |
| `POST /api/v1/invitations/accept`                                    | JSON `{token}`; authenticated account | `200`, household representation consistent with existing `HouseholdSnapshot`, and `Cache-Control: no-store` | `401` unauthenticated; `403` CSRF; `400` malformed body/token syntax; `404` unknown, expired, revoked or consumed token with same generic response; `409` active account membership or no household capacity without disclosing household details |

Use existing RFC 9457 error schema and logging policies. Invalid input messages must never interpolate the supplied token. Authorization occurs in application operations, not solely controllers. IDs identify resources but never grant authority. Check security config, existing HTTP behavior and OpenAPI tests for compatibility; no existing operation/schema is removed or altered. A shareable code suffices; building and delivering a full URL is outside the backend contract.

A revocation racing acceptance has exactly one serialized result: if revocation commits first acceptance fails; if acceptance commits first revocation finds consumed state. Expiration is checked after acquiring locks. The create response is the only plaintext secret disclosure; persistence, subsequent read, error and logging paths cannot return it. The 24-hour deadline and token syntax are documented as API fields without real examples or secrets.
