# Responsibility contract (proposed for HO-12)

## Module boundary

Add a narrow named household interface (exact Java types may follow established conventions) with an operation that, within an existing transaction, locks a requested household and returns the authenticated actor only if currently an active member, plus an eligibility check resolving a supplied account to its active membership in that household. Both operations execute after the household lock and keep it through transaction completion; no client actor ID. Absent identity is unauthenticated; absent/foreign household is indistinguishable. It exports neither membership repository nor global existence. `HouseholdLookup.isAccessible` is unchanged. Read paths authorize at application boundary. The contract's transaction precondition and lock order must be documented and tested; future deactivation uses the same lock protocol.

## HTTP

All routes require authenticated session; unsafe requests require CSRF. UUID path variables: `householdId`, `responsibilityId`; paths are scoped under `/api/v1/households/{householdId}/responsibilities`. Resource response fields: `id`, `householdId`, `title`, nullable `description`, `mode` (`INDIVIDUAL`), `status` (`ACTIVE|PAUSED|ARCHIVED`), `ownerAccountId`, nonnegative integer `version`. Historical archived owner may be inactive. Body version is mandatory for every mutation of an existing responsibility, an integer between 0 and 9223372036854775807; absence, null, negative, fractional, out-of-range or invalid shape gives 400. Creation accepts no client version and initializes its version to 0. HTTP schema and handlers must agree on required, nullable, unknown properties and enum validation. For create and full-replacement details requests, omitted `description` and explicit null both mean no description; an empty string is retained as an empty description. For a details update, omission therefore clears any previous description rather than leaving it unchanged. Comparing a proposed value for no-op detection uses the resulting value. Unknown properties in every responsibility request are rejected with 400 `VALIDATION_ERROR` and no mutation, including fields such as `status` or `mode` on an endpoint that does not define them. Set `additionalProperties: false` on the corresponding request schemas and implement request-scoped enforcement without changing unrelated endpoints; test rejection at the HTTP boundary. This is a new endpoint policy, not an assumption about existing Jackson defaults. The only optional input fields are `description` on create and details, and `ownerAccountId` on restore. On restore, omission means use the historical owner; explicit `null`, empty string, non-string or malformed UUID is invalid and must produce 400 without mutation. The OpenAPI restore schema must omit `ownerAccountId` from `required` but declare a non-null UUID string; the implementation must distinguish absence from explicit null. Invalid JSON types or malformed UUIDs use existing `INVALID_VALUE`; explicitly null owner uses `VALIDATION_ERROR`. Description accepts only string or null when present; wrong types produce `INVALID_VALUE` rather than coercion. Required title and mode must be JSON strings; owner IDs must be UUID strings; version must be a JSON integer without string, boolean, decimal or overflow coercion. Schema and HTTP tests must cover absent, null, malformed, wrong-type and coercion attempts for each required field and each optional field, and persisted state after rejection.

No generic mode switching or completed endpoint exists. Explicit unsupported mode and transition requests reject without mutation; controllers must not silently ignore unexpected mode/status properties. When approved spec requires rejection for mode-switch attempts, unknown properties or explicit unsupported change operations must be rejected consistently, not silently accepted. Requests without `view` are rejected as invalid to avoid silently collapsing the separate queries. Document all required fields, path parameters, 400/401/403/404/409/415 responses, `VERSION_CONFLICT`, and CSRF in OpenAPI. Use existing RFC 9457 Problem Details; define stable error codes for invalid owner and invalid state consistent with project conventions. Foreign and nonexistent resources yield identical 404. Current-version invalid transition is a 409 with a distinct stable state-conflict code; stale is `VERSION_CONFLICT` 409. Validation of malformed JSON or unauthenticated/unauthorized access may precede version evaluation, but for authorized accessible valid-shape commands stale version precedes no-op, eligibility and transition rules. Include negative HTTP and application tests.

## Compatibility

New routes and new interface are additive; no existing route or `HouseholdLookup` method is altered. The existing version-conflict contract continues. V9 adds mandatory persistence fields and rejects populated legacy placeholder data; old binaries that insert old-format rows must not operate after migration. Quiesce writers for upgrade and deploy compatible code with migration. Preserve task composite FK. No user-data migration, deletion or downstream task work is implied.
