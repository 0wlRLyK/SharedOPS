# Implementation Plan: Individual Responsibility Ownership

**Branch**: `feat/HO-12-responsibility-ownership` | **Date**: 2026-11-23 | **Spec**: [spec.md](spec.md)

## Summary

Deliver household-scoped INDIVIDUAL responsibility creation, editing, owner transfer, pause/resume/archive/restore and separate current/archived reads. Version-checked writes and transfer facts are transactional; household membership eligibility is serialized against membership changes. SHARED mode, tasks, recurrence, deletion and activity UI remain outside this slice. See [research](research.md), [data model](data-model.md) and [HTTP and module contracts](contracts/responsibilities.md).

## Technical Context

**Language/Version**: Java 25. **Dependencies**: existing Spring Boot 4.1.1, Security, Modulith, JDBC/JPA, Flyway and validation; no new dependency. **Storage**: PostgreSQL, production Flyway migrations. **Testing**: JUnit/AssertJ, MockMvc, Testcontainers PostgreSQL, production migrations, controlled `Clock`. **Target**: existing backend HTTP service. **Performance**: preserve pilot small-workload requirements; no new numerical target. **Constraints**: tenant isolation at application boundary, no secrets in evidence, body-version conflict convention, no data loss in migration. **Scale**: household of at most two active members; no pagination promises for these current lists beyond existing requirements.

## Design and compatibility

1. Add a household-owned exported contract providing authenticated actor authorization and transactional access to active member eligibility under the existing household row serialization point. Keep identity and membership repositories internal. It must obtain the household lock **before** checking actor/owner membership; lock scope remains through the caller's transaction. Reads check membership at the application boundary. Contract returns only eligibility/actor facts needed for the operation, not global member discovery. Add, rather than change, the existing `HouseholdLookup.isAccessible` contract. Tests verify callers cannot bypass authorization and boundaries remain valid.
2. Use a responsibility domain aggregate with allowed status transitions and nonblank title rule, plus application ports and transaction boundary. An inaccessible or missing resource yields the same 404; invalid owner and unsupported mode have consistent validation failures. For creation, acquire the household lock, validate actor and owner, then insert at version 0 without a client-supplied version. For an authorized mutation of an accessible existing responsibility, acquire the household lock, load/lock the responsibility, compare supplied version before no-op or lifecycle-state evaluation, validate owner under lock where needed, then conditionally persist. The database write must include the expected version; if an update affects zero rows or a flush detects a version conflict, map it to `VERSION_CONFLICT` 409 and roll back. An unchanged detail or same-owner transfer returns current representation with no version/audit change. Repeated lifecycle requests with a current version are rejected; stale version still returns 409. Household lock serializes writers and a conditional version guard protects correctness even if a writer bypasses service assumptions.
3. Persist exactly one historical membership owner reference tied to its household; current records require active owner. Migration uses composite same-household referential integrity and `INDIVIDUAL`/status checks. A database-side invariant protocol must serialize responsibility inserts/owner or status changes and membership deactivation on the household row, and reject deactivation if it would leave a current responsibility with an inactive owner. This preserves the invariant across direct SQL and future membership writers, not merely a check before write. HO-85 must transfer affected current responsibilities before deactivating membership and use the same lock order; archived owner references remain valid. Exercise both lock orders and committed outcomes against PostgreSQL; detect and handle any deadlock as a failed transaction, never as success. Do not implement account deletion here. The DB constraint/trigger must not prohibit household purge after dependent rows are removed in a controlled transaction.
4. V1 has only `id` and `household_id` and cannot supply title or owner for existing placeholder rows. V9 must abort transactionally with a clear diagnostic if any exist; do not invent owners, drop rows, or touch linked tasks. Empty upgrades add required fields/constraints and preserve `(id, household_id)` task foreign key. Existing tests inserting bare responsibility rows after migration need valid fixtures. Populated legacy installations need a separately approved data-preserving migration before upgrade. This is an explicit deployment compatibility limitation, not an assertion that production is empty.
5. Store immutable explicit-transfer facts (responsibility, household, actor, time, old and new owner) in the same transaction as the guarded owner change. Clock instant is controlled and persisted as an instant. Failure of fact persistence or final commit rolls back both. No audit fact for no-op, invalid, stale or restore owner replacement unless separately specified. Archive/restore/transfer never write tasks. The V1–V8 task table contains only `id`, `household_id` and `responsibility_id`; assignment and terminal status do not yet exist. Test existing linked rows and prohibit task writes using a test-only fail-on-write trigger during success paths; for rejected paths assert the expected rejection and committed row unchanged. HO-12 cannot directly verify assignment or completion/reopening fields until HO-18 implements them; HO-18 must add the full end-to-end regression. This is a verification coverage limitation, not a relaxation of the no-reassignment/no-reopen requirement.
6. Add the endpoints and schemas in [contracts/responsibilities.md](contracts/responsibilities.md) to authoritative `docs/api/openapi.yml` alongside implementation. This is additive HTTP surface; each existing-resource mutation body requires a nonnegative integer version; creation supplies no version and returns initial version 0. Details is a full replacement: omitted or null description clears the existing value, while an empty string remains distinct. Restore owner omission uses the historical owner; explicit null and malformed or incorrectly typed UUIDs are 400 without mutation, so the adapter must distinguish omitted from null. Description accepts only string or null, with no coercion; contract tests cover all optional-field cases and persisted outcomes. Task design must include HTTP/schema cases for missing, null, wrong JSON types and coercion attempts in required title, mode, owner and version, including malformed UUID, negative, fractional and out-of-range version; rejected cases assert unchanged committed state. Reject unknown properties with a structured 400 for responsibility requests only; define `additionalProperties: false` and test runtime/schema agreement without changing other endpoint behavior. Existing Problem Details conventions and CSRF/session protections remain. Existing OpenAPI declares no responsibility operations, so no existing response is changed. Unknown external consumers of household exports are unaffected by adding an operation on a new interface; validate architecture and contract. Database change requires coordinated migration and compatible deployments; old application writers cannot create valid responsibility rows after V9.
